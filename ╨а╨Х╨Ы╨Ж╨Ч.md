# 🚀 Як випустити реліз (варіант А — за тегом)

---

## Коротко

```bash
git tag v3.1.1
git push origin v3.1.1
```

Усе. Через ~15 хвилин у Releases буде `v3.1.1` з `.exe`, `.dmg` і `latest.yml`.

**Версію задає тег.** `package.json` правити не обов'язково — workflow сам
підставить туди версію з тега перед збіркою.

---

## Чому саме так

Автопідняття версії робив старий `auto-version.yml`, який я видалив. Він:

1. робив `npm version patch`
2. комітив зміну
3. пушив назад у `main`
4. **цей push знову запускав усі workflow** → цикл
5. і створював реліз **без файлів**

Тег такої проблеми не має: він не змінює гілку, тому зворотного push-а немає
і зациклитись неможливо.

---

## Що тепер робить workflow

### Push у `main` → тільки перевірка

```
🟢 check   ~1 хв
   ├─ npm install          (ловить зламані залежності)
   └─ перевірка синтаксису
```

Релізу **не створює**. Це страховка: якби вона була раніше, помилка
`electron-updater@^7.0.0` вилізла б одразу, а не після кількох днів пошуків.

### Push тега `v*` → повний реліз

```
🟢 release (windows-latest)  ~6-10 хв
🟢 release (macos-latest)    ~8-15 хв
   ├─ версія береться з тега (v3.1.1 → 3.1.1)
   ├─ підставляється в package.json
   ├─ збірка
   └─ публікація в Releases
```

---

## Три способи випустити

### 1. Тільки тег (найшвидше)

```bash
git tag v3.1.1
git push origin v3.1.1
```

`package.json` у репозиторії залишиться з 3.1.0 — це нормально, workflow
підставляє версію сам. Але щоб не плутатись, краще спосіб 2.

### 2. З оновленням package.json (рекомендовано)

```bash
npm run release:patch      # 3.1.0 → 3.1.1, підкаже наступні команди

git add package.json
git commit -m "Release v3.1.1"
git tag v3.1.1
git push origin main --tags
```

Так версія в репозиторії завжди збігається з останнім релізом.

Для мінорної: `npm run release:minor` (3.1.0 → 3.2.0)

### 3. Вручну через інтерфейс GitHub

```
Actions → Build and Release → Run workflow
└─ Version: 3.1.1
└─ Run workflow
```

Зручно, коли ви не за комп'ютером із git.

---

## Правила версій

```
3.1.0 → 3.1.1   patch   виправлення помилок
3.1.0 → 3.2.0   minor   нові функції
3.1.0 → 4.0.0   major   великі зміни
```

Головне — **версія має зростати**. `electron-updater` пропонує оновлення
тільки якщо в релізі версія більша за встановлену.

---

## Якщо помилились із тегом

```bash
# видалити локально і на GitHub
git tag -d v3.1.1
git push origin :refs/tags/v3.1.1

# видалити реліз: Releases → v3.1.1 → Delete
# потім поставити тег заново
```

---

## Перевірка результату

```
Ваш репо → Releases → v3.1.1
```

Має бути **4 файли**:

| Файл | Для чого |
|------|----------|
| `SvarogCommandCenter Setup 3.1.1.exe` | інсталятор Windows |
| `SvarogCommandCenter-3.1.1.dmg` | інсталятор macOS |
| `latest.yml` | авто-оновлення Windows |
| `latest-mac.yml` | авто-оновлення macOS |

**Якщо `latest.yml` немає — авто-оновлення не працюватиме.** Це головний
файл, за яким встановлена програма розуміє, що вийшла нова версія.

## Часті питання

**Чи можна ставити тег на старий коміт?**
Так: `git tag v3.1.1 <hash>`. Збереться саме той стан коду.

**Що як запушити тег, який уже існує на GitHub?**
Push відхилиться. Спочатку видаліть старий тег (див. вище).

**Чи спрацює, якщо тег без `v`?**
Ні. Тригер налаштований на `v*`. Тег `3.1.1` не запустить нічого.

**Чи потрібен GH_TOKEN у Secrets?**
Ні. Використовується вбудований `secrets.GITHUB_TOKEN`, який GitHub створює
автоматично на кожен запуск.

**Чому реліз не з'явився, хоча збірка зелена?**
Перевірте: Settings → Actions → General → Workflow permissions →
**Read and write permissions**. Без цього публікація падає з 403.
